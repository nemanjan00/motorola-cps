# GM600 Firmware Analysis (full flash dump)

Analysis of `motofix.BIN` (repo root): a complete 256 KB dump of the GM600's firmware
flash (U0102, AT29C020). Firmware **R03.03.21**, `Copyright 1992, Motorola, Inc.`

Findings from the glasgow-rib project (nemanjan00/glasgow-rib, `gm600/PROTOCOL.md`,
`FIRMWARE.md`, `DUMP_SEQUENCE.md`) were derived from a **single-bank** 64 KB CPU-space
dump read over BUS+ from a different radio with the same firmware version. Every address
they publish has been re-verified byte-for-byte against this full-chip dump; where this
dump adds something new it is marked **[new]**.

## Hardware

| Part | Designator | What |
|---|---|---|
| CPU | U0101 | 68HC11 K-series (parts list: masked 68HC11K4 `5195136A01`; schematic label 68HC11K1_QFP). 768 B RAM, 640 B EEPROM, K-series MMU |
| Flash | U0102 | Atmel AT29C020, 256 KB, TSOP-32 (5 V-only, 256-byte pages, software data protection; parts list may show 28F020 — reads identically, writes differ) |
| SRAM | U0103 | 32 KB "hybrid" SRAM, probably battery-backed |

## Dump provenance and integrity

Read out of circuit on an XGECU T48. First attempt (`mot9to1.BIN`) is **corrupt** — kept
as the reference twin:

- The T48 reported a **single-pin contact error**; the chip was read anyway.
- In `mot9to1.BIN`, **bit 3 is set in all 262,144 bytes**: exactly half of the byte-value
  space (all values with bit 3 = 0, including `0x00`) never occurs. Data line **D3 (I/O3,
  chip pin 17 on DIP/PLCC)** was floating/stuck high.
- Pin 9 (tied high to get the read to run) is **A3**, an address input — unrelated to the
  data corruption. The address path in both dumps is clean: no address-bit duplication
  pattern anywhere in the file.

After reseating the chip, `motofix.BIN` read clean. Proof the only defect was D3:

```
mot9to1.BIN[i] == motofix.BIN[i] | 0x08   for every byte (0 exceptions)
```

Healthy metrics for `motofix.BIN`: all 256 byte values present, 12,581 `0x00` bytes,
96k bytes changed vs the bad dump (36.8%), overall entropy 5.26 bits/byte.

## Flash layout and banking

The flash holds 16 × 16 KB pages. The K-series MMU maps one page at a time into the
banked CPU window `0x4000`–`0x7FFF` via the **bank select register `0x1058`**;
**bank register value = page << 2**.

Address translation for this dump:

| Region | Mapping |
|---|---|
| Banked page `p` at CPU `0x4000`–`0x7FFF` | `file = cpu − 0x4000 + p*0x4000`, bank reg `p<<2` |
| Fixed bank, CPU `0x8000`–`0xFFFF` | `file = cpu + 0x30000` (pages 14–15) |

Per-page fill (0xFF = erased):

| Page | Bank reg | File range | % 0xFF | Notes |
|---|---|---|---|---|
| 0 | 0x00 | 0x00000–0x03FFF | 53.3 | |
| 1 | 0x04 | 0x04000–0x07FFF | 37.8 | SBEP dispatch + handlers (below) |
| 2 | 0x08 | 0x08000–0x0BFFF | 71.3 | |
| 3 | 0x0C | 0x0C000–0x0FFFF | 58.6 | |
| 4 | 0x10 | 0x10000–0x13FFF | 0.8 | densest page; 0x2D/0x2E targets live here |

| 6 | 0x18 | 0x18000–0x1BFFF | 14.7 | **[new]** populated, although glasgow-rib's used-bank list skips 0x18 |

glasgow-rib's "banks used by firmware" list (`00 04 08 0C 10 14 1C 20 24 28 2C`) was
derived from the one bank their BUS+ dump contained. **[new]** Page 6 (reg 0x18) is
populated in this full-chip dump — its contents are presumably mapped in from a bank
they hadn't captured. Page 13 is fully erased; page 12 nearly so.

**Far-call trampoline** at CPU `0x87B5` (file `0x387B5`) — verified: the byte stream
contains `ldab 0x1058` / `ldab #2` / `stab 0x1058`. Each of the 504 call stubs from
CPU `0x87D9` is `jsr 0x87B5` followed by a 3-byte `[bank, addr_hi, addr_lo]` descriptor
located at `stub + 3 + 0x4CAC`.

## Firmware anchors verified in this dump

- **Vector table** file `0x3FFD4`–`0x3FFFF` ↔ CPU `0xFFD4`+ : default/unused ISR
  `0x8EE4` = `20 FE` (`bra *`, halt loop); COP-fail / clock-monitor / reset vectors all
  = **`0xD45A`**.
- **Reset code** at CPU `0xD45A` (file `0x3D45A`) — textbook HC11 startup:

  ```asm
  sei
  ldaa #$01
  staa $3d            ; CONFIG-related write
  ldx  #$1000         ; register block base
  ldaa #$bb
  staa $39,x          ; 0x1039 = OPTION
  ldaa #$40
  staa $35,x          ; ...
  ```

- **Register-init table** at CPU `0xD437` (file `0x3D437`): `[reg, value]` pairs into the
  `0x1000` block, terminated by the first value ≥ `0x80`.
- **Copyright string** CPU `0x803C` (file `0x3803C`, preceded by byte `0x50`);
  **version `R03.03.21`** CPU `0xCDC5` (file `0x3CDC5`).
- **SBEP dispatch table** at CPU `0x4019` in bank 04 (file `0x4019`), entry =
  `0x4019 + 2*opcode`, big-endian. All 32 entries `0x10`–`0x2F` match glasgow-rib
  exactly (see command table below); unpopulated opcodes point at the shared
  unsupported-stub `0x8236`.
- **Handler spot checks** (all verified):
  - `0x10` enter-programming: entry `0x4CD5` = `pshb psha jsr $9BCA`; target `0x9BCA`
    (file `0x39BCA`) = `0F 20 FE` = `sei; bra *` — a deliberate hang, so the COP watchdog
    resets the CPU into programming mode. Explains the captured "ACK, then the radio
    resets" behavior.
  - `0x13` max-block query: handler `0x4C8E` contains `ldd #$0020` + `ldab #$82` —
    the `82` reply payload `00 20 00` is a **hardcoded constant**, not a real limit.
  - `0x26` backdoor: handler `0x4CDC` = `pshb psha sei tsx ldx … jmp ,x` — jumps to an
    address taken from the request with interrupts off. **Never send blind.**
- **[new]** `0x2D`/`0x2E` dispatch entries (`0x8B8A`/`0x8B87`) point **into the far-call
  stub table** itself, i.e. these handlers are banked routines reached through the
  trampoline. Their descriptors (file `0x3D836`/`0x3D839`) decode to **bank `0x10`
  (file page 4), targets CPU `0x6E14` / `0x6D24`** (file `0x12E14` / `0x12D24`) — real
  code, purpose unknown.

## SBEP command set (radio side, authoritative)

Wire framing, timings and DPS evidence: `DPS_EMEA_600SERIES_R00.03.02/PROTOCOL.md`.
This table is the firmware truth, from the dispatch table above.

| Op | Handler (bank 04) | Meaning | Notes |
|---|---|---|---|
| `10` | `4CD5`→`9BCA` | Enter programming mode | `sei; bra *` → COP watchdog reset |
| `11` | `4D85` | Read block | reply `0x80`, 3-byte header = address echoed as sent; only low 16 address bits used; `0D80`–`0FFF` special-cased to internal EEPROM |
| `12`, `14`–`16`, `1A`–`1F`, `24`, `25`, `27`–`2C`, `2F`+ | `8236` | unsupported stub | no useful reply |
| `13` | `4C8E` | Query max block size | returns constant `00 20 00`; 64-byte reads work; >64 B refused with a bare `0x80` status byte (not ACK) |
| `17` | `4CE8` | Write block | reply `84` OK / `85` fail; same EEPROM special-case as `11` |
| `18` | `4E49` | **Self-test / verify** (read-only) | sub-command byte: `0` = status-check fixed region, `1` = checksum/compare over region; returns status byte; not sent by DPS |
| `19`, `21`, `22`, `23` | `4F30` | Query family (shared message-post path) | reply formatted by a task in another bank; `19`/`21`/`22` likely queries, not destructive writes |
| `20` | `4F3F` | Parameter read / softpot write | data byte 2: `0` = read (reply `8A`), `1`/`2` = write (RAM vs permanent flavors) |
| `26` | `4CDC` | **Factory backdoor: jump to address from request** | `sei`, pointer from request, `jmp` — document, don't fire |
| `2D` | `8B8A` (stub) | unknown | trampoline → bank `0x10`, CPU `0x6E14` |
| `2E` | `8B87` (stub) | unknown | bank `0x10`, CPU `0x6D24` |

Note the **opcode-number collisions with other families** (same numbers, different
meaning): on Waris/Commercial-series radios `0x18` = write serial number
(`REQ_WR_SERNUM`) and `0x26` = `REQ_INVOKE` — do not carry those meanings onto the
600 series.

## Control head interface (SPI) — LED byte, LCD buffer

The front panel is on the CPU's SPI bus (`SPI_CLCK_BUF`, `SPI_DATA_BUF`, `LCD_CE_BUF`,
`LED_CE` on J0101), not on BUS+. Firmware anchors (fixed bank, verified by linear
disassembly that stays in sync across the whole region):

- **SPI transfer routine `0x9102`**: X = buffer, B = count, Y = 0x1000; bit-bangs SPDR
  (`0x102A`) waiting on SPSR.SPIF (`tst $1029; bpl`).
- **Device dispatcher `0x8F1F`**: B = device index (≤14), jumps through the word table at
  **`0x8F44`** after enabling SPI (`anda/staa $1028`). Chip selects are bits 0/5/6 of the
  port at **`0x107E`** (`bset`/`bclr 126, y`).
- **Table entry 10 → `0x8F64`**: sends **1 byte from RAM `0x34AE`** and pulses a CE —
  this is the **front-panel LED shift register push**. So `ldab #10; jsr $8F1F` =
  "update LEDs" anywhere in firmware (seen at bank04 `0x59AE`, bank00 `0x5BB1` right
  after writing `0x34AE`).
- **`0x34AE` = LED shadow byte.** At bank04 `0x5994` an update preserves only bit 7
  (`andb #$80`) and merges 7 fresh bits — bit 7 is a persistent flag, bits 0–6 are
  per-state LED bits. Bank00 `0x5BAE` writes `0xFF`/`0xEF` (LED test / startup pattern).
- **Table entry 8 → `0x8F7F`**: sends 21 bytes from `0x37AC` — the LCD buffer.
- Entries 2/3/4 (`0x8FB7`/`0x8FD6`/`0x8FF0`): 13/3/2-byte transfers from `0x01F1`,
  `0x01EE`, `0x01FE` — serial peripherals, one of them the ASFIC (GCB outputs include
  `AUDIO_PA_ENABLE` = RX unmute). Which entry is the ASFIC is not yet proven (linear
  decode in bank 04 drifts; needs proper control-flow disassembly).

**Display (corrected 2026-11-12 — the earlier `0x37AC` digit map here was wrong).** The glass has
two controllers. `0x37AC` (entry 8, 21 bytes) drives the **icons/framing only** and never changes with
the displayed number. The **three 7-segment digits** (and 9 icons) are a separate start-bit-framed
serial controller driven by entry 5 (`0x9018`, select `0x61`); the firmware caches the 5-byte struct
`[b0 b1 d0 d1 d2]` it last sent at **`0x3495`** (digit bytes `0x3497`–`0x3499`, ASCII at `0x34BD`).
Found by RAM-diffing the live radio at two displayed numbers. The idle number **is** the codeplug Own
Unit No. at `0x0F0B` (BE16) — confirmed on hardware (322 → 456 → 712). The emulator once rendered the
same screen for any `0x0F0B`; the cause was unmodelled input pins/A/D (it sat in a channel scan), not
runtime derivation — with the bench radio's measured inputs it boots to 322 / 456 like the radio.
Full write-up, segment map and photos: glasgow-rib `gm600/FIRMWARE.md` ("7-seg digits", "Keypad, key
events and the receive flags") and `gm600/images/lcd_segments/`.

**Squelch chain (from schematic + vectors):** SQDET (carrier, ASFIC H1) → MCU input pin
(not yet identified in code); PLLIM (filtered/limited PL tone, ASFIC A4) → U0101 pin 10
(PA1/IC2); the tone-valid decision is firmware. **RAM receive flags (found 2026-11-12 by
RAM-diffing no signal / carrier / carrier + correct PL):** `0x347F` = carrier detected, `0x347E` = PL
decoded = RX active / squelch open (input-state array `0x3460 + event`). OC3/OC4/OC5 ISRs (`0x92A1`/`0x92AA`/
`0x9298`) clear their flag and `jmp` through RAM pointers `$A4/$A6/$A2` — a task
dispatcher; the RX/squelch task hangs off one of these. Vector map (CPU `0xFFD6`+):
SCI/SPI/PAI unused (default `0x8EE4`), TOF `0x9347`, IC1 `0x9262`, RTI `0x92E1`.

## No flash-write path exists in the firmware

Checked exhaustively in this dump:

- The SBEP dispatch table **ends at opcode `0x2E`** (entries past `0x2F` are data, not
  pointers). There is no flash/erase/program command.
- The **AT29C020 software-data-protection unlock sequence** (`0xAA→0x5555`,
  `0x55→0x2AAA`) appears **nowhere** in the 256 KB, in any addressing mode.
- The `0x17` write handler (`0x4CE8`) has exactly two paths: `0x0D80`–`0x0FFF` →
  internal-EEPROM write (`0x9ED4`), everything else → `0xCE79`, a **plain memory
  copy** (`ldaa 0,x / staa 0,y` loop — no unlock, no polling). Flash writes through it
  are silently eaten by the chip's SDP.
- The `ldab #$55 / stab $103A / ldab #$AA / stab $103A` sequences found in bank 00
  (e.g. file `0x007B9`) are the **COP watchdog reset** (COPRST = `$103A`), not a flash
  unlock.

Conclusion: the radio was flashed at the factory with a pre-programmed chip or via
68HC11 bootstrap mode (MODA/MODB strap — the mask-ROM loader is in the CPU, not in this
flash). There is no field firmware-update path, matching DPS being a codeplug-only tool.

**Consequence for patching:** flash writes must come from code running outside the
flash. The building blocks exist over SBEP: `0x17` writes RAM (via the `0xCE79` memcpy
path) and `0x26` jumps anywhere — so a small flasher stub can be uploaded to SRAM,
executed via `0x26`, and do the SDP unlock + 256-byte page program itself. Note `0x26`
runs with interrupts off and the COP still runs, so the stub must feed COPRST or finish
fast. Patch space: pages 12–13 (file `0x30000`–`0x37FFF`, nearly/fully erased, not boot
blocks). Check boot-block lockout before relying on the first/last 8 KB.

## In-circuit patch development over SBEP (no soldering)

The flash chip never needs to come off the board. Everything iterates in RAM over BUS+
(SBEP `0x11`/`0x17`/`0x26`), and RAM-only experiments are **self-healing: a power cycle
restores stock behavior**, so a bad experiment costs one reboot, not a bricking.

1. **Find the squelch flag dynamically.** `0x11` reads work on a live radio. Dump the RAM
   regions (`0x0000`–`0x02FF`, `0x1080`–`0x3FFF`) twice — squelch closed vs. open with
   valid tone — and diff. The tone-valid flag flips between the two dumps. (Same method
   glasgow-rib used to separate live RAM from stored data.)
2. **Hook execution through RAM, not flash.** The OC3/OC4/OC5 ISRs (`0x92AA`/`0x92A1`/
   `0x9298`) clear their flag and then `jmp` through **RAM pointers `$A6`/`$A4`/`$A2`**.
   Save the original pointer, write your stub's address into it with a `0x17` RAM write,
   chain to the original at the end of the stub. That gives periodic execution with no
   flash change. (Reset re-initializes these pointers, which is what makes experiments
   self-healing — and why permanence needs step 4.)
3. **Stub skeleton for "LED follows tone squelch":** read the flag found in step 1,
   set/clear one bit of the LED shadow `0x34AE`, push with `ldab #10; jsr $8F1F`,
   feed COP if running long (`$55`,`$AA` → `$103A`), chain. RAM blocks per `0x17` write
   are limited by the 261-byte receive buffer (~250 data bytes), ample for a stub.
   Pick stub RAM that never changes in the step-1 dumps.
4. **Permanence (optional, still no soldering):** once proven, upload a flasher stub to
   SRAM via `0x17`, run it via `0x26`; the stub does the AT29C020 SDP unlock + 256-byte
   page program (code must run from RAM — it can't erase the bank it executes from).
   Put the patch in erased page 12/13 (file `0x30000`–`0x37FFF`) and point the hook
   there. First/last 8 KB boot blocks may be locked — check lockout status in
   product-ID mode before counting on them. `motofix.BIN` remains the recovery image.

Note: the SRAM is probably battery-backed, so a RAM-resident patch may survive power
cycles in practice — but the task-pointer hooks are re-initialized at reset, so only a
flashed patch is truly permanent.

- Which MCU pin SQDET lands on, and where the RX task computes the squelch/tone-valid
  flag (needed for an LED-reflects-tone-squelch patch; LED mechanism documented above).
- Which ASFIC SPI device entry (2/3/4) carries GCB0 = AUDIO_PA_ENABLE.
- Bit-to-physical-LED map for `0x34AE` (determine experimentally).
- What page 6 (bank reg `0x18`) holds and which code maps it in.
- Exact `0x18` self-test sub-command semantics and region boundaries.
- Codeplug per-block checksum scheme (see glasgow-rib `gm600/CODEPLUG.md` and our
  `DPS_EMEA_600SERIES_R00.03.02/CODEPLUG_BITMAP.md`).
- Whether SBEP `0x17` can reprogram flash regions — **resolved: no** (plain memcpy, no
  SDP unlock anywhere in firmware; see "No flash-write path exists in the firmware").
- Behavior of `19`/`21`/`22` beyond the shared query entry point (reply formatter bank).
